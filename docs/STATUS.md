# Status

The claims pilot is built, following `docs/PLAN.md`: a backend, a dashboard for the handlers and the UnderCover Agent. The harness build, following `docs/PLAN_HARNESS.md`, has the agent run the queue from a to-do list, hand each claim to a fresh claim agent, look up the wording and the claims manual by section, and recover from failures. The durable build, following `docs/PLAN_DURABLE.md`, adds the payout rules, tracing in Langfuse, the records on Supabase, a claim agent that waits for a sign-off and carries on, and work that survives a restart. The swarm build, following `docs/PLAN_SWARM.md`, replaces the queue agent with a dispatcher that works many claims at once, and adds the cost and time of every claim, evaluations and a scoreboard.

## Run it

- `uv sync` and `npm install`. Put `OPENROUTER_API_KEY` in `.env`. Set `MODEL_NAME` to use another model, such as `openrouter/free`.
- Put `DATABASE_URL` (the Supabase session pooler connection string), `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL` in `.env` too. Without the Langfuse keys nothing is traced. The agent's service needs `DATABASE_URL`.
- Settings are read from the environment when needed (`agent/settings.py`): `BACKEND_URL` (default http://localhost:8000, the address the agent uses to reach the backend, so set it if the backend is on another port), `UNDERCOVER_AGENT` (default http://127.0.0.1:8002, the address of the agent's service, which the backend calls), `DATABASE_URL`, the Langfuse keys, `OPENROUTER_API_KEY` and `MODEL_NAME`. A real environment variable beats `.env`. `npm run dev` starts the backend and the agent's service with `--env-file .env`; `uv run -m agent` loads `.env` itself.
- Tracing: with `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL` set, each claim's work is traced in Langfuse as one session named for the claim's thread (such as `CLM-1004-c598a7fa`). Langfuse's sessions endpoint is gone for new organizations; read a session through `GET /api/public/v2/observations` with a `sessionId` filter.
- Logs: the backend logs to the terminal. A crashed run is logged with its traceback, and each ended attempt logs one line (claim, run, state, failed, seconds). The team sees only the kind of error in a step.
- `npm run dev` starts the backend (port 8000), the agent's service (port 8002) and the dashboard (port 5173, open http://localhost:5173).
- The database: with `DATABASE_URL` in the backend's environment (`npm run dev` passes `.env`) the backend uses Supabase, with all its tables in the `undercover` schema; without it, SQLite in `backend/undercover.db` (git-ignored). The tests and the end-to-end tests never set it. Either way the tables are created and seeded from `data/` on first start. `npm run seed` starts again from the seed data on whichever database is in use (Supabase when `.env` has `DATABASE_URL`): stop the backend first. The backend holds at most 4 connections. For a trial with the real model, reseed first and cap the run at five claims.
- Run the agent from the command line while the backend and the agent's service run: `uv run -m agent CLM-1001` works one claim, and carries on a stopped one by name. There is no command for the whole queue: a dispatch works it (`agent/dispatcher.py`), started from the dashboard's "Dispatch the queue" panel. A dispatch works every claim in progress and every waiting claim, oldest submitted first, with up to N claim agents at once (1 to 25, 3 to start with). Only one dispatch runs at a time.
- A sign-off on the dashboard (a handler and "Sign off") is saved first. The claim is then in progress while the backend calls the agent's service, which resumes the claim's saved thread and pays it. If the service is not running the sign-off stands and the claim waits in progress for the next run.
- `npm run check` runs every check: ruff, pyright and pytest at 80% coverage; ESLint, Prettier, tsc and vitest at 80% coverage; Playwright. `npm run e2e` runs only Playwright, on its own backend (port 8001), dashboard (port 5174), a stand-in for the agent's service (port 8003, `e2e/agent.mjs`, which records each call and pays the claim) and a new SQLite database in the temp folder, so it never touches the dev database, Supabase or the real service. `npm run check` is green with `.env` moved out of the way: the tests set `DATABASE_URL`, the Langfuse keys and `UNDERCOVER_AGENT` to values that reach nothing.

## What is built

- `backend/`: FastAPI and SQLAlchemy Core on Supabase or SQLite. Every operation has an `operation_id`, a one-line docstring and no optional inputs.
  - Reads: `list_claims`, `get_claim`, `get_policy`, `get_claim_history` (by claim id: the customer's earlier claims plus every claim in this system filed before it, decided or open; no contact details), `list_document_sections`, `get_document_section` (the policy wording and the claims manual, by section), `get_instructions` (the claim agent's, at `/api/instructions/claim`), `list_handlers`, `list_steps`.
  - Writes: `calculate_payout` (the payout rules in `backend/payout.py`, from section 10 of the wording and `data/plans.json`; the limit is `payout_approval_limit` in `data/company.json`), `decide_claim`, `pay_claim`, `sign_off_claim`, `add_step`, `run_agent`, `record_model_call` and `record_work_time`, and for the dispatcher `create_dispatch`, `plan_run` (the claims a dispatch works), `start_claim` (starts a waiting claim or carries on one in progress, as the same attempt), `end_attempt`, `end_run`, `stop_runs`, `get_latest_dispatch` and, for the dashboard, `start_dispatch` (asks the agent's service through `backend/agent_service.py`, which also holds the call that works a claim: 503 "The agent's service could not be reached." when it is not running, and its 409 passed through) (the dispatch with its claims, cost, times and a summary built from the records). One dispatch runs at a time (409).
  - The modules: `main.py` (the app, start-up and error handlers), `api_claims.py` and `api_runs.py` (the routes), `deps.py` (the connection and the agent a route is given), `decisions.py` (decisions, payments and sign-off, with the rules), `attempts.py` (steps, attempts, threads, retries and carrying on), `runs.py` (dispatches, their claims and summary), `usage.py` (model calls and working time), `work.py` (running the claim agent through the agent's service at `UNDERCOVER_AGENT`, ending an attempt, logging), `queries.py`, `documents.py`, `instructions.py`, `models.py` and `db.py` (SQLAlchemy Core, SQLite or Postgres), `tables.py` and `seed.py`. A test replaces the agents with FastAPI dependency overrides (`work.claim_agent`) through the `agents` fixture in `conftest.py`.
  - The rules are in `decisions.py` and `attempts.py`. Every write that reads first runs in one transaction (`backend/db.py`: `BEGIN IMMEDIATE` on SQLite, `FOR UPDATE` on the claim or run row on Postgres), so two requests cannot both pass a check, and the database backs this with foreign keys, one open attempt per claim and one running run. A decision is refused (422) when its payout is not finite, is not above 0 for an approval, is more than the amount claimed, or when its explanation or policy section is empty or the section is not one of the wording's or the manual's. Texts have length limits. A decision is recorded once, and the same decision again counts as done (a different one is a 409). An approval over $1,000 (`payout_approval_limit` in `data/company.json`) ends in `waiting_for_sign_off`, and `pay_claim` is refused with a 409 until `sign_off_claim`, which records the handler and the time, moves the claim to `in_progress` and hands it to the agent, which pays it (the payment copies who signed off and when). A payment must equal the approved payout and happens once; the same payment again counts as done.
  - A claim the agent is working on stays `in_progress` until its attempt ends, then settles to `decided` or `waiting_for_sign_off`. Each try is an attempt. An attempt that crashes, ends with no decision, or ends with an approval of $1,000 or less that is not paid puts the claim back to `waiting` with an error step; a second failed attempt leaves it in the state `left_for_handler`, which the agent cannot change. A stop is not a failure: if the agent's service goes away or cannot be reached while it works, the attempt stays open on its thread (`attempts.thread_id`) and the claim stays `in_progress`. Nothing is failed on start. The next dispatch, or "Run agent" on the claim, carries on every claim left in progress, from its open attempt's thread. A 409 from the agent's service (the claim is already being worked there) is a stop too. A start that cannot reach the service at all gives the claim back to `waiting` without counting an attempt. The database changed in the harness build: delete `backend/undercover.db` with the backend stopped to reseed. The quality build (`docs/PLAN_QUALITY.md`) added foreign keys and indexes, which a new database gets, so reseed after pulling it.
  - The claim agent's instructions are `backend/instructions_claim.md`; `backend/instructions.py` fills in the approval limit, the filing window and the repeat-claim rule from `data/company.json` when it serves them. The backend loads only `claims.json`, `policies.json`, `customers.json`, `handlers.json`, `company.json`, `policy_wording.md` and `claims_manual.md` from `data/`, and for the answer key, only when seeding, `data/evals/decisions.json`, `held_out_claims.json` and `held_out_decisions.json`; a test checks it. It never reads `data/evals/harder`, `data/evals/even_harder`, `data/security/` or `knowledge.json`. Seeding stores the held-out claims (`held_out_claims`) and the handlers' decisions on both sets (`answer_key`) in tables of their own; only `backend/evaluations.py` reads them, and a test checks that.
- **Evaluations** (`backend/evaluations.py`, `backend/scoring.py`): `create_evaluation` copies the claims of the evaluation set (the 25 claims of the queue) or the held-out set, or just the five `tiny` ones, into `claims` with new ids such as `EV7-CLM-1004` and `claims.evaluation_id` set, and records them in `run_claims`. `list_evaluations` and `get_evaluation` score an evaluation from the backend's own records: `decision_accuracy`, `accuracy` (decision matches, payout within a dollar), the cost of mistakes (wrongful decline $1,500, wrongful approval its payout whether or not it was paid, needless referral $50, a wrong amount the difference), `straight_through`, model cost per claim, time per claim (the mean of each claim's work seconds in the run) and the run's time (none while running or when stopped). A claim the agent did not decide counts as a referral. Copies never show in the queue (`list_claims`), a dispatch never lists them, and a copy's claim history is the customer's seeded claims plus the earlier claims of its own evaluation, so evaluations and the queue cannot affect each other. A copy approved over the limit settles as `decided` with no payment ("held for sign-off counts as finished"), `sign_off_claim` and `run_agent` refuse a copy, and the harness deletes its saved progress. `get_claim` on a copy shows nothing from the handlers' decisions. The service starts one at `POST /evaluations`, and the backend at `start_evaluation`.
- `agent/dispatcher.py`: the dispatcher, a LangGraph graph with no model and no checkpointer. `list_claims` asks the backend for the dispatch's claims (`plan_run`), a conditional edge sends one `Send` for each, and the `work_claim` worker runs with `max_concurrency` set to N. A `check_again` node after the whole round sends the claims that went back to `waiting` once more. The worker has a `RetryPolicy` on `ModelRateLimitError` and `ModelTimeoutError` (waits of 5, 10 and 20 seconds), and an `error_handler` that leaves a claim in progress for the next dispatch when the retries run out, so no error stops the dispatch. It needs LangGraph 1.2.19: in 1.2.12 a failure the handler caught still raised when several workers ran at once.
- `agent/main.py`: the claim agent, a hand-written LangGraph graph (`ClaimNodes`) with its own state, in place of `create_agent`. `run(claim_id, thread_id)` fetches its instructions from the backend and works the claim on a thread. Nodes: `agent` (the model, with a retry policy), `tools` (the seven tools built for the claim by `claim_tools(claim_id)`: `get_claim`, `get_policy`, `get_claim_history`, `list_document_sections`, `get_document_section`, `calculate_payout`, `decide_claim`; none takes a claim, policy or customer id; a refusal or a failing tool comes back to the model as text), `check` (reads the claim from the backend and routes), `approval` (`interrupt()`, waiting for a sign-off) and `pay`. `main.work_claim(claim_id, run_id, new_saver)` is the one function the dispatcher calls: it takes an in-process lock on the claim (a claim the service is already working is skipped), starts or carries on the attempt, runs the graph with a checkpointer of its own, and ends the attempt. A rate limit or timeout passes through with the attempt open; any other error fails the attempt. The graph starts at `check`, so a claim that already has an approval is paid without the model. After a decision it pays an approval straight away, or waits when the backend says `needs_sign_off`; it never applies the limit itself, and the agent has no tool to pay. At most 30 model calls (the 31st stops the claim with an error). Every node records its steps on the claim, and each section read is a `read` step. Progress is saved after every step (`durability="sync"`); `run` starts a new thread, carries on a stopped one from its last step, or resumes a waiting one once the backend has the sign-off. The default model is `openai/gpt-6-luna` with low reasoning effort (`MODEL_NAME` chooses another, which runs with no effort set, recorded as `none`). Each model reply's tokens and OpenRouter's cost are recorded with the claim and its run (`model_calls`, through `record_model_call`), and each stretch of the agent's work on a claim is timed and recorded (`work_times`, through `record_work_time`), a failed stretch included. A pause for a sign-off ends a stretch, so the wait is never counted. A run id is empty outside a run. It reaches the backend only over HTTP; a test checks that it reads no files.
- `agent/service.py`: the agent's service (port 8002, `UNDERCOVER_AGENT` is its address), which `npm run dev` starts beside the backend and the dashboard. `POST /claims/{claim_id}/work` with a `thread_id` runs `main.run` on a shared checkpointer, for "Run agent" and after every sign-off (409 if the claim is already being worked here). `POST /dispatches` with `concurrency` (1 to 25) refuses with a 409 while a dispatch or evaluation is running, otherwise has the backend create the dispatch (`create_dispatch`), answers 202 with its id and works it on a background thread (`dispatcher.run_dispatch`), then ends the run `finished`, or `failed` if the graph raises. Each claim agent gets a `PostgresSaver` of its own, built over one pool of at most 4 connections to Supabase in the `undercover` schema, which they wait for for up to two minutes. When it starts it waits for the backend (up to 20 seconds) and marks any dispatch still running as `stopped`. It needs `DATABASE_URL` and stops with a plain message without it. It flushes the Langfuse traces after each claim.
- `dashboard/`: React, Vite and TypeScript, in the brand's look, light and dark. Its API types are generated from the backend (`npm run types` writes `dashboard/src/api-types.ts` from `uv run -m backend.openapi`; `npm run check:python` fails if it is out of date, so run `npm run types` after changing `backend/models.py`). A refused action shows the backend's own reason, polling pauses while the tab is hidden, and list keys stay unique when a text repeats. The Claims view has the "Dispatch the queue" panel (a number of claim agents from 1 to 25, 3 to start with, and "Start a dispatch", refused with the backend's reason while a run is going or when the agent's service is not running; then the latest dispatch with its state, model cost, time, the sum of its claims' times, a row for each claim with where it stands, its decision, start time, time and cost, refreshed every 2 seconds while it runs, and the summary built from the records when it ends), the queue (a count for each of five states, every claim) and the selected claim in full, with "What it read" listing the sections the agent looked up. A waiting claim has "Run agent". While the agent works, "What the agent did" lists its steps, refreshed every 2 seconds. A claim waiting for sign-off has a handler picker and "Sign off and pay". The Scoreboard view starts an evaluation (a set, "Just the 5 tiny claims", and 1 to 25 claim agents at once, 3 to start with) and lists the evaluations newest first with every measure in a table that scrolls inside its panel (percentages as whole numbers, model cost per claim to four places). An evaluation opens to its claims: the handler's decision and payout beside the agent's, a miss marked "Miss" in Raspberry (a different decision, or a payout more than a dollar off), and each claim linked to its page, which opens in the Claims view with an "Evaluation copy" label, no sign-off form and no "Run agent". It refreshes every 2 seconds while an evaluation runs. The Instructions view shows the claim agent's instructions, read only.  The queue refreshes every 2 seconds.
- `e2e/`: Playwright tests of the dashboard. They set up decisions and steps through the API, and a run directly in the test database, and never run the agent.

## Checked live (swarm build)

On 4 November 2026, on Supabase with the default model (`openai/gpt-6-luna`, low reasoning), after one `npm run seed` and with `npm run dev`:

- **N=3, stopped.** Dispatch 1 (N=3) started 09:01:02. After about two minutes `kill -9` on both processes on port 8002 stopped `npm run dev`. CLM-1001 was decided and paid and CLM-1008 and CLM-1011 were held for sign-off. CLM-1010, CLM-1015 and CLM-1018 were in progress, each with one open attempt and 11 to 12 checkpoints, and the run was still `running`. Starting `npm run dev` again marked it `stopped`.
- **N=25.** Dispatch 2 (N=25) worked the 22 claims left (the other three were done or held). It carried on CLM-1010, CLM-1015 and CLM-1018 as the same attempts, each with one attempt and its original thread, and the 19 claims worked from the start all began within 3 seconds, so every claim ran at once. The run took 45.0 seconds against 684.2 seconds for its claims' times added up. It cost $0.0196, with 16 approvals (one held for sign-off), 4 declines and 2 referrals. A sign-off of CLM-1008 in a real browser while it ran paid 3.4 seconds after the click. No claim failed and no step recorded an error.
- **Connections.** `pg_stat_activity` for the postgres user, polled every second for the whole check (and once through the Supabase MCP server), never showed more than 10, counting the connections Supabase and the poller hold, against a limit of 12.
- **Evaluation of the evaluation set, N=25** (evaluation 4): `decision_accuracy` 80%, `accuracy` 80%, cost of mistakes $2,919.00, straight through 92%, model cost per claim $0.0011, time per claim 43.4 seconds, run time 55 seconds. It missed CLM-1018, CLM-1025 and CLM-1019 (approved $330.00, $71.00 and $98.00 where the handlers referred), CLM-1012 (approved $920.00 where the handlers declined) and CLM-1023 (declined where the handlers referred). The queue's counts (23 decided, 2 waiting for sign-off) were the same before and after.
- **Evaluation of the held-out set's five `tiny` claims, N=5** (evaluation 5): all five matched the handlers, so `decision_accuracy` and `accuracy` 100%, no cost of mistakes, straight through 80%, $0.0011 per claim, 19.0 seconds per claim, 27 seconds in all. The queue's counts were unchanged.
- **Langfuse.** The 25 claims of evaluation 4 are found together by the tag `run-4`: 25 traces in 25 sessions.
- **Not as planned.** Evaluation 3 (the first try of the evaluation set at N=25) stalled and is still on the Scoreboard: 18 copies were left in progress and 7 failed on backend timeouts, so its 24% means nothing. Dispatch 2's and evaluation 3's traces in Langfuse carry no session or tag, because the claim graph then ran inside the dispatcher's run. Dispatch 1's 24 model calls were recorded with a cost of $0.00, since OpenRouter's `usage.cost` is 0 on a key of our own.

Three problems the live runs found are fixed, each with a test:

- **The backend stalled at N=25.** A route took its database connection in a dependency, used it in another thread and returned it in a third. With more requests waiting than the pool holds, the waiters filled the 40 request threads and the requests holding a connection could never get a thread to return it, so every request waited out the 60-second timeout. A route now takes and returns its connection in its own thread (`with_db`), and `backend/tests/test_pool.py` reproduces the stall with one connection and three threads.
- **Cost was $0.** On a key of our own OpenRouter reports the model's price in `cost_details.upstream_inference_cost` and only its fee in `usage.cost`, so both are added when `is_byok` is true.
- **A claim lost its Langfuse session and tag** when it ran inside the dispatcher's worker. `work_claim` now runs each claim in a context of its own.

Where the time goes at N=25: a claim took about 43 seconds against about 22 at N=3. The model's calls took the same time (2.0 seconds at N=3, 1.6 to 2.1 at N=25). The backend calls grew: a tool call's mean from 0.07 to 0.22 seconds, the tools node's from 1.0 to 2.6 seconds and the check node's from 0.15 to 0.43 seconds. That is 25 claim agents sharing the backend's 4 connections to Supabase, each call a few round trips. Cutting the backend's queries for each call, or the steps it records, would cut it; more connections are not allowed.

## Open items

- The time of a stretch that was killed with its process is not recorded, and neither is its cost, so a claim carried on by the next dispatch shows only the stretch that dispatch worked.
- At N=25 each claim takes about twice as long as at N=3, because the backend's calls wait for its 4 connections (see above).
- A dispatch ends `finished` even when claims were left in progress after their retries ran out; its summary lists them, and the next dispatch carries them on.

- Payouts may vary between runs of the same claim, because the model chooses the lines it sends to `calculate_payout`. Scoring the agent against `data/evals/` is for a later build.
- The claim agent reads many sections for each claim (10 to 14 in the live check), more than the instructions strictly need. Narrowing that would cut cost.
- A claim left for a handler stays there: handlers have no way yet to return it to the queue or decide it from the dashboard.
- A handler can only sign off a held payout. Rejecting it, and the note back to the agent, are for a later build.
- Several tool failures are returned to the model as text rather than retried (the graph's retry policy covers the model; `call` retries a connection that fails).
- The `undercover` tables on Supabase have row level security off. The schema is not one the Supabase API serves, but turn it on with policies before anything else reads them.
- The Instructions view shows the Markdown marks as they are written.
- Sign-in, real payments and messages to customers are not built, as the spec says.
