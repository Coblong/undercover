# Status

The claims pilot is built, following `docs/PLAN.md`: a backend, a dashboard for the handlers and the UnderCover Agent. The harness build, following `docs/PLAN_HARNESS.md`, has the agent run the queue from a to-do list, hand each claim to a fresh claim agent, look up the wording and the claims manual by section, and recover from failures. The durable build, following `docs/PLAN_DURABLE.md`, adds the payout rules, tracing in Langfuse, the records on Supabase, a claim agent that waits for a sign-off and carries on, and work that survives a restart.

## Run it

- `uv sync` and `npm install`. Put `OPENROUTER_API_KEY` in `.env`. Set `MODEL_NAME` to use another model, such as `openrouter/free`.
- Put `DATABASE_URL` (the Supabase session pooler connection string), `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL` in `.env` too. Without the Langfuse keys nothing is traced. The agent's service needs `DATABASE_URL`.
- Settings are read from the environment when needed (`agent/settings.py`): `BACKEND_URL` (default http://localhost:8000, the address the agent uses to reach the backend, so set it if the backend is on another port), `UNDERCOVER_AGENT` (default http://127.0.0.1:8002, the address of the agent's service, which the backend calls), `DATABASE_URL`, the Langfuse keys, `OPENROUTER_API_KEY` and `MODEL_NAME`. A real environment variable beats `.env`. `npm run dev` starts the backend and the agent's service with `--env-file .env`; `uv run -m agent` loads `.env` itself.
- Tracing: with `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL` set, each claim's work is traced in Langfuse as one session named for the claim's thread (such as `CLM-1004-c598a7fa`). Langfuse's sessions endpoint is gone for new organizations; read a session through `GET /api/public/v2/observations` with a `sessionId` filter.
- Logs: the backend logs to the terminal. A crashed run is logged with its traceback, and each ended attempt logs one line (claim, run, state, failed, seconds). The team sees only the kind of error in a step.
- `npm run dev` starts the backend (port 8000), the agent's service (port 8002) and the dashboard (port 5173, open http://localhost:5173).
- The database: with `DATABASE_URL` in the backend's environment (`npm run dev` passes `.env`) the backend uses Supabase, with all its tables in the `undercover` schema; without it, SQLite in `backend/undercover.db` (git-ignored). The tests and the end-to-end tests never set it. Either way the tables are created and seeded from `data/` on first start. `npm run seed` starts again from the seed data on whichever database is in use (Supabase when `.env` has `DATABASE_URL`): stop the backend first. The backend holds at most 4 connections. For a trial with the real model, reseed first and cap the run at five claims.
- Run the agent from the command line while the backend and the agent's service run: `uv run -m agent` works every waiting claim as one run, `uv run -m agent --limit 5` works at most five and leaves the rest waiting, and `uv run -m agent CLM-1001` works one claim. A run first carries on any claim a stopped agent left in progress, or that was signed off while the agent was away, and takes over a run left going (`Carrying on run 3.`), keeping that run's limit. `uv run -m agent CLM-1001` carries on a stopped claim by name. The dashboard has "Run the queue" (a number of claims) and, on a waiting claim, "Run agent"; it does not offer a new run while one is left going, so use the command line to finish it.
- A sign-off on the dashboard (a handler and "Sign off") is saved first. The claim is then in progress while the backend calls the agent's service, which resumes the claim's saved thread and pays it. If the service is not running the sign-off stands and the claim waits in progress for the next run.
- `npm run check` runs every check: ruff, pyright and pytest at 80% coverage; ESLint, Prettier, tsc and vitest at 80% coverage; Playwright. `npm run e2e` runs only Playwright, on its own backend (port 8001), dashboard (port 5174), a stand-in for the agent's service (port 8003, `e2e/agent.mjs`, which records each call and pays the claim) and a new SQLite database in the temp folder, so it never touches the dev database, Supabase or the real service. `npm run check` is green with `.env` moved out of the way: the tests set `DATABASE_URL`, the Langfuse keys and `UNDERCOVER_AGENT` to values that reach nothing.

## What is built

- `backend/`: FastAPI and SQLAlchemy Core on Supabase or SQLite. Every operation has an `operation_id`, a one-line docstring and no optional inputs.
  - Reads: `list_claims`, `get_claim`, `get_policy`, `get_claim_history` (by claim id: the customer's earlier claims plus every claim in this system filed before it, decided or open; no contact details), `list_document_sections`, `get_document_section` (the policy wording and the claims manual, by section), `get_instructions` (for `queue` or `claim`), `list_handlers`, `list_steps`.
  - Writes: `calculate_payout` (the payout rules in `backend/payout.py`, from section 10 of the wording and `data/plans.json`; the limit is `payout_approval_limit` in `data/company.json`), `decide_claim`, `pay_claim`, `sign_off_claim`, `add_step`, `run_agent`, and for the queue agent's runs `start_run` (a required `limit`), `get_latest_run`, `write_todos`, `work_claim` (a fresh claim agent on one claim, answering in one line) and `finish_run` (refused while the run has missed a waiting claim). A run counts the claims it starts and refuses a new one past its limit; a claim waiting for a retry never counts again.
  - The modules: `main.py` (the app, start-up and error handlers), `api_claims.py` and `api_runs.py` (the routes), `deps.py` (the connection and the agents a route is given), `decisions.py` (decisions, payments and sign-off, with the rules), `attempts.py` (steps, attempts, threads, retries and carrying on), `runs.py` (a run, its limit and to-do list), `work.py` (running the agents through the agent's service at `UNDERCOVER_AGENT`, ending an attempt, logging), `queries.py`, `documents.py`, `instructions.py`, `models.py` and `db.py` (SQLAlchemy Core, SQLite or Postgres), `tables.py` and `seed.py`. A test replaces the agents with FastAPI dependency overrides (`work.claim_agent` and `work.queue_agent`) through the `agents` fixture in `conftest.py`.
  - The rules are in `decisions.py` and `attempts.py`. Every write that reads first runs in one transaction (`backend/db.py`: `BEGIN IMMEDIATE` on SQLite, `FOR UPDATE` on the claim or run row on Postgres), so two requests cannot both pass a check, and the database backs this with foreign keys, one open attempt per claim and one running run. A decision is refused (422) when its payout is not finite, is not above 0 for an approval, is more than the amount claimed, or when its explanation or policy section is empty or the section is not one of the wording's or the manual's. Texts have length limits. A decision is recorded once, and the same decision again counts as done (a different one is a 409). An approval over $1,000 (`payout_approval_limit` in `data/company.json`) ends in `waiting_for_sign_off`, and `pay_claim` is refused with a 409 until `sign_off_claim`, which records the handler and the time, moves the claim to `in_progress` and hands it to the agent, which pays it (the payment copies who signed off and when). A payment must equal the approved payout and happens once; the same payment again counts as done.
  - A claim the agent is working on stays `in_progress` until its attempt ends, then settles to `decided` or `waiting_for_sign_off`. Each try is an attempt. An attempt that crashes, ends with no decision, or ends with an approval of $1,000 or less that is not paid puts the claim back to `waiting` with an error step; a second failed attempt leaves it in the state `left_for_handler`, which the agent cannot change. A stop is not a failure: if the agent's service goes away or cannot be reached while it works, the attempt stays open on its thread (`attempts.thread_id`) and the claim stays `in_progress`. Nothing is failed on start. The next run (`uv run -m agent`, "Run the queue" or "Run agent") carries on every claim left in progress, from its open attempt's thread, and takes over a run left going rather than starting a second. A start that cannot reach the service at all gives the claim back to `waiting` without counting an attempt. The database changed in the harness build: delete `backend/undercover.db` with the backend stopped to reseed. The quality build (`docs/PLAN_QUALITY.md`) added foreign keys and indexes, which a new database gets, so reseed after pulling it.
  - The agents' instructions are `backend/instructions_claim.md` and `backend/instructions_queue.md`; `backend/instructions.py` fills in the approval limit, the filing window and the repeat-claim rule from `data/company.json` when it serves them. The backend loads only `claims.json`, `policies.json`, `customers.json`, `handlers.json`, `company.json`, `policy_wording.md` and `claims_manual.md` from `data/`; a test checks it. It never reads `data/evals/`, `data/security/` or `knowledge.json`.
- `agent/queue.py`: the queue agent, `run_queue(run_id)`. Its four tools are `list_waiting_claims`, `write_todos`, `work_claim` and `finish_run`. It plans a to-do list, hands each claim to a fresh claim agent through `work_claim`, and is reminded up to twice if it stops before `finish_run`. It never reads a claim.
- `agent/main.py`: the claim agent, a hand-written LangGraph graph (`ClaimNodes`) with its own state, in place of `create_agent`. `run(claim_id, thread_id)` fetches its instructions from the backend and works the claim on a thread. Nodes: `agent` (the model, with a retry policy), `tools` (the seven tools built for the claim by `claim_tools(claim_id)`: `get_claim`, `get_policy`, `get_claim_history`, `list_document_sections`, `get_document_section`, `calculate_payout`, `decide_claim`; none takes a claim, policy or customer id; a refusal or a failing tool comes back to the model as text), `check` (reads the claim from the backend and routes), `approval` (`interrupt()`, waiting for a sign-off) and `pay`. The graph starts at `check`, so a claim that already has an approval is paid without the model. After a decision it pays an approval straight away, or waits when the backend says `needs_sign_off`; it never applies the limit itself, and the agent has no tool to pay. At most 30 model calls (the 31st stops the claim with an error). Every node records its steps on the claim, and each section read is a `read` step. Progress is saved after every step (`durability="sync"`); `run` starts a new thread, carries on a stopped one from its last step, or resumes a waiting one once the backend has the sign-off. The default model is `deepseek/deepseek-v4.1-flash`. It reaches the backend only over HTTP; a test checks that it reads no files.
- `agent/service.py`: the agent's service (port 8002, `UNDERCOVER_AGENT` is its address), which `npm run dev` starts beside the backend and the dashboard. `POST /claims/{claim_id}/work` with a `thread_id` runs `main.run` with a synchronous `PostgresSaver` on a pool of at most 2 connections to Supabase, in the `undercover` schema. It needs `DATABASE_URL` and stops with a plain message without it. The backend calls it for every attempt and after every sign-off. It flushes the Langfuse traces after each call.
- `dashboard/`: React, Vite and TypeScript, in the brand's look, light and dark. Its API types are generated from the backend (`npm run types` writes `dashboard/src/api-types.ts` from `uv run -m backend.openapi`; `npm run check:python` fails if it is out of date, so run `npm run types` after changing `backend/models.py`). A refused action shows the backend's own reason, polling pauses while the tab is hidden, and list keys stay unique when a text repeats. The Claims view has a "Run the queue" panel (a number of claims, a button, and the latest run with its to-do list and summary, refreshed every 2 seconds while it runs), the queue (a count for each of five states, every claim) and the selected claim in full, with "What it read" listing the sections the agent looked up. A waiting claim has "Run agent". While the agent works, "What the agent did" lists its steps, refreshed every 2 seconds. A claim waiting for sign-off has a handler picker and "Sign off and pay". The Instructions view shows the queue agent's and the claim agent's instructions, read only. The queue refreshes every 2 seconds.
- `e2e/`: Playwright tests of the dashboard. They set up decisions and steps through the API, and a run directly in the test database, and never run the agent.

## Open items

- Payouts may vary between runs of the same claim, because the model chooses the lines it sends to `calculate_payout`. Scoring the agent against `data/evals/` is for a later build.
- The claim agent reads many sections for each claim (10 to 14 in the live check), more than the instructions strictly need. Narrowing that would cut cost.
- A claim left for a handler stays there: handlers have no way yet to return it to the queue or decide it from the dashboard.
- A handler can only sign off a held payout. Rejecting it, and the note back to the agent, are for a later build.
- A stopped run shows as Running on the dashboard until the next run takes it over from the command line.
- Several tool failures are returned to the model as text rather than retried (the graph's retry policy covers the model; `call` retries a connection that fails).
- The `undercover` tables on Supabase have row level security off. The schema is not one the Supabase API serves, but turn it on with policies before anything else reads them.
- The Instructions view shows the Markdown marks as they are written.
- Claims are worked one at a time. Several at once is not built.
- Sign-in, real payments and messages to customers are not built, as the spec says.
